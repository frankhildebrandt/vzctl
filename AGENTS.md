## Learned User Preferences

- Antworten immer auf einfachem, kurzem Deutsch; nicht ausschweifen.
- Analysen, Vergleiche und Implementationspläne bevorzugt als Canvas aufbereiten und bei Plan-Änderungen mitaktualisieren.
- Plan-Reviews mit explizit genanntem Modell (z. B. Fable, GPT-SOL) als Subagent; ohne Angabe Parent-/Auto-Modell erben, kein stiller Override.
- GitHub-Issues für vzctl sollen implementationsreif, spezifisch und mit Findings/Dependencies verknüpft sein.
- Nach Slice-Abschluss: Fertigstellung prüfen, Issues schließen und nachtragen, Canvas aktualisieren, Folgeprompt erzeugen; Commit/Push wenn gewünscht.
- Destruktive UI-Aktionen (Löschen usw.) immer über Bestätigungs-Modal.
- Topology-/Projekt-Edits schreiben immer `hypernetwork.config.yaml` (Source of Truth; Projekte auch so anlegbar).
- UI-Unterseiten: kontextuelle Sidebar; „Zurück“ nur bei tieferer Navigation (Dashboard-Escape liegt separat in der Brand-Zeile); Settings unten in der Nav; OIDC-Stack-Overrides gehören in die Stack-Config (nicht Host-Settings).
- Stack entfernen (`down --purge`): VMs hart stoppen/löschen (SIGKILL), keine Rücksicht auf Datenverlust; normales Stack-down bleibt graceful.
- Builds warning-frei halten (Rust/Swift lokal ohne Warnings).
- `make install` stoppt laufende Agents vor Binary-Replace; `vz-net` nur graceful (bootout/SIGTERM, kein SIGKILL) wegen CIDR-Orphans.

## Learned Workspace Facts

- `vzctl` ist ein CLI-first DevStack-/Hypervisor-Projekt auf Apple Virtualization.framework (Environments as Code für macOS-VMs).
- Privates GitHub-Repo unter `frankhildebrandt`; Planungsdokumente liegen unter `docs/planing/` (Plan, Reviews, Decision Log, Canvas); Lizenz ist `vzctl Public License v1` (AGPL-inspiriert, source-available, Affero-Copyleft für Modifications, kein Verkauf und kein kommerzielles Bundling/OEM).
- Mindest-macOS-Version ist 26; Pre-26 ist unsupported.
- Prozessmodell: Control-Plane (`vz-supervisor`) + HyperNetwork-Supervisor `vz-net` (vmnet-Refs + Host-Bridges, `net.sock`) + Host-Dataplane `vz-edge` (DNS/Ports/Ingress/Caddy/Dex/`oidc-simple`, `edge.sock`, Spec `docs/specs/vz-edge-v1.md`) + ein Helper pro VM (owns `VZVirtualMachine`); CP owns Desired-State/SQLite/Apply; Startreihenfolge `vz-net` → `vz-edge` → `vz-supervisor`; Install-Stop umgekehrt (supervisor → edge → vz-net); Helper nur Attachment-Handles via Serialize; Console-/exec-TTY-Attach über UDS unter `helpers/`; Detach mit Ctrl-P Ctrl-Q; nur Entitlement `com.apple.security.virtualization` (`com.apple.vm.networking` bei ad-hoc codesign → SIGKILL); LaunchAgent-/Job-PATH muss Homebrew (`/opt/homebrew/bin`) enthalten, sonst scheitert `docker`/`docker context`.
- Repo-Layout: Rust-CLI unter `crates/vzctl`, Swift-Daemon unter `daemon/` (`vz-net`, `vz-edge`, `vz-supervisor`, `vz-helper`), UI unter `apps/vzctl-ui` (Tauri + React/TypeScript, TanStack Router/Query; Topology-Editor auf AntV X6; i18n `deDE`/`enUS` mit System-Default und Settings-Umschalter; Fehler-Tab `/errors` mit Session-History + Clipboard-Copy; Bake/Seal/Pull mit Live-Job-Log inkl. Builder-Serial), öffentliche Doku unter `apps/docs` (Astro + Starlight, DE, globale Top-Nav, GitHub Pages `https://frankhildebrandt.github.io/vzctl/`); Runtime-State unter `~/Library/Application Support/vzctl/` (UDS + SQLite); Supervisor-REST Control-Plane Spec `docs/specs/supervisor-rest-v1.md` (Default `unix:$VZCTL_STATE_DIR/api.sock`, konfigurierbar via `VZCTL_API_LISTEN`/`--api-listen`; VM-IDs `{project}/{vm}` in Pfaden encoded lassen — Pfad nicht vor Segment-Split dekodieren); `vz-net` Contract `docs/specs/vz-net-v1.md`; UI spricht REST über Tauri-`invoke`/`api_request` (nicht Browser-fetch); Terminal bleibt Tauri-UDS; Release-Artefakte via `make package` / `scripts/package-macos.sh` (`.tar.gz`, `.pkg`, `.dmg`).
- Internes DNS stellt `vz-edge` bereit (Zone `{vm}.{net}.{project}.vz.test`); Host-Listener `127.0.0.1:15353`, macOS löst über `/etc/resolver` auf — Schreiben braucht Root via `vzctl dns install-resolver|uninstall-resolver` bzw. REST `POST|DELETE /v1/dns/resolver` (Apply/UI elevaten per Admin-Dialog; sonst `Permission denied`); Guest-Nameserver ist Bridge `.0:53` — Port 53 kommt vom Root-LaunchDaemon `vz-dns-bind` (SCM_RIGHTS) via `vzctl dns install-bind-helper` (ohne Helper: `Permission denied` / `dns_ok=false`; Helper muss Port bei UDS-Hangup freigeben); auf Custom-vmnet ist Host-Gateway/DNS `.0` (nicht `.1`), Router typisch `.2`, Guests `.10+`; Cross-Net nur über Router-VM.
- Stacks sind deklarativ per Verzeichnis/Git-Repo und `hypernetwork.config.yaml` (`apiVersion: hypernetwork/v1`, Spec `docs/specs/hypernetwork-v1.md`, `vzctl validate`) steuerbar (`plan|diff|up|apply|down|adopt`); Bootstrap/Mutationen per `vzctl stack init` und `stack vm|net|volume|mount add|remove` (validiert, atomisches Schreiben); `adopt` ist report-only (stale Helper-Locks melden, kein Mutate/Reclaim); unvollständige Apply-Journals per `--resume`/`--abort`; Referenzbeispiel `examples/edge-dmz`; VMs ohne explizites Netz landen im konfigurierbaren Default-Netz (shared, voller Egress/NAT); hypernetwork kann optional `cpus`/`memory` durchreichen; Apply-Pipeline inkl. CA/OIDC/Ingress (Caddy/Dex oder `mode: oidc-simple` Dev-IdP, `*.svc.{project}.vz.test`); bei mehreren passenden Routern `policies.*.via` setzen (sonst Apply-Fehler); OIDC-Uplink: Host-Defaults unter Application Support (Secrets nicht in Git), Stack-Overrides in `hypernetwork.config.yaml`.
- VMs teilen ein sealed Base-Image (APFS linked clone / clonefile + pro-VM dataDisk); Identity (machine-id, NIC/MAC, SSH-Host-Keys, cloud-init instance-id) wird pro Clone neu gesetzt; Base nie writable öffnen; `vm create` speichert `resources.{cpus,memory_mib}` (Defaults 2/1024), optional `--root-password` per NoCloud cloud-init — keine Default-Passwörter; Runtime-IDs aus Stacks sind `{project}/{vm}` (Config-Keys bleiben kurz; manuelles Create ohne `--project` flach; mit `--project` wird prefix’t); Bundle unter `vms/{project}/{vm}/`.
- CLI-Contract: `docs/specs/cli-contract-v1.md` (JSON-Envelope, stdout=Daten / stderr=Diagnostics, stabile Exitcodes); `up|apply|down` mit `--progress plain|ui|off` (`up|apply` nutzen bei Human-TTY standardmäßig das Job-Dashboard, `down` und Non-TTY bleiben `plain`; JSON ohne expliziten Progress bleibt still); VM-Lifecycle/Tools u. a. `vzctl vm list|start|stop|restart|delete|ps|inspect|exec|attach|transfer|services|logs|mount|unmount|mounts|agent upgrade` (IPs in list/ps aus Netz-Attachments; `vm logs`/`inspect.logs.serial` aus Serial-Log; `vm transfer` max. 256 KiB); `vzctl image list|pull|bake|seal`; `vzctl dns status|query|install-resolver|uninstall-resolver|install-bind-helper`; `vzctl docker` (`ps|inspect|start|stop|restart|run`, SSH-Context `vzctl-{project}`); `vzctl oidc status`; `vzctl port list` (Host-Forwards 127.0.0.1); `vzctl services status|start|stop|restart` (Host-LaunchAgents net/edge/supervisor); interaktives `vm exec -it` braucht Capability `exec_tty`.
- Docker-Role: `roles: [docker]` → SSH-User `vzctl` + Key unter `projects/{project}/docker/`, Label `vzctl.dev/dns-services=docker` → `docker.svc.{project}.vz.test`; `cloudInit` wird mit System-NoCloud gemerged; Port-Forwards via Supervisor-Userspace-Proxy (nicht TCP 2375); `networks.*.backend: docker` exponiert die Docker-Bridge als Hypernetwork-CIDR (Owner `roles: [docker, router]`, bip `.2`, kein vmnet; Peer-Router bekommen Static Routes); deklarative Container auf Docker-VMs via `composeFiles` + `containers` (Apply-Step `ensure_containers` nach `ensure_docker_context`, ensure-only mit Labels `vzctl.dev/managed`); virtiofs-Mounts deklarativ (`spec.volumes` + `vms.*.mounts`) und live (`vm mount` / share-swap + Guest-Agent `fs.mount`, Spec `docs/specs/virtiofs-v1.md`).
- Guest-Agent-Wire-Contract: `docs/specs/guest-agent-v1.md` (virtio-vsock, length-prefixed JSON, Token-Auth); Guest-Utils (Agent + Helper-Skripte) live via `vzctl apply` (`ensure_guest_utils`) bzw. `vzctl vm agent upgrade` — Re-Bake nur für neue Base-Images; Token dauerhaft unter `/var/lib/vzctl/agent.token` (nicht `/run` — cloud-init `write_files` nur once-per-instance); bei PTY-exec muss `Ctty` Kind-FD 0 sein (nicht Parent-`pts.Fd()`); Capability `fs_mount` für virtiofs-Bind; Helper fällt bei `fs.mount unsupported` auf `exec`+`virtiofs-bind` zurück (wie CLI); `vzctl-agent` hat passwordless sudo (`NOPASSWD`, u. a. virtiofs/router/CA) — sonst scheitern Guest-Helpers an „no new privileges“.
- Base-/Image-Pull zielt auf ARM64 Cloud/Server-Images (nicht Installer-ISOs); Aliases u. a. `ubuntu|debian|alpine|arch|fedora|rocky|alma|opensuse|coreos|flatcar|photon|opensuse-microos|talos-latest` (Contract `docs/images/pull-contract-v1.md`); Workflow `pull → bake --tag → seal --tag` (CLI/REST brauchen `--tag`/`body.tag`); Config pinnt sealed Artefakte per `spec.images.*.tag` (`baked|sealed/<canonical>@<tag>.raw`); Apply skippt Bake/Seal wenn Tag schon sealed; Bake/Seal nutzen lokales `virt-customize` oder die gepinnte Builder-VM-Appliance (`scripts/build-builder-appliance.sh`, Cache unter `images/builder/`); Builder-Helper ohne erreichbaren Supervisor → leere Attachments → NAT-Fallback; Builder-Work-Dirs und Unix-Sockets müssen unter macOS `AF_UNIX` `sun_path` (~104 Bytes) bleiben — kurze `/tmp/vzb-{token}`-Pfade und kurze exec-TTY-Namen unter `helpers/` (lange `vzctl-builder-{nanos}`-Pfade brechen Bake); Progress über `VZCTL_PROGRESS`/Job-Log; v0.2 Ingress/OIDC/CA + Tauri-UI sind gelandet (v0.1 war Alpha).
